# Mundo Meller

## Purpose

Create an immersive, conversion-oriented Meller showroom inside Shopify without compromising store stability, accessibility, maintainability, or Core Web Vitals.

The experience may resemble a premium physical store, but commerce remains primary: every interaction must help the customer discover, compare, understand, and purchase products.

## Non-negotiable operating rules

1. Never modify the published theme unless the user explicitly authorizes that exact action.
2. Work in a named duplicate theme and confirm store, market, theme name, and theme ID before any write.
3. Present the visual and functional contract before construction.
4. Separate reversible preparation from critical writes.
5. Request explicit authorization before creating or updating Shopify theme files, products, metafields, app settings, navigation, scripts, or tracking.
6. Preserve a rollback path for every applied batch.
7. Never hardcode live stock, price, availability, product URLs, or variant state.
8. Never claim completion without evidence from desktop, mobile, functional, and performance verification.

## Required workflow

### 1. Establish scope

Confirm:

- Shopify store and market.
- Exact duplicate theme name.
- Page type: landing, home module, full showroom, collection experience, or proof of concept.
- Product scope: all products, selected collection, families, shapes, use types, or campaign subset.
- Whether real 3D assets already exist.
- Whether the reference image is a direction or an exact visual contract.
- Required integrations: cart drawer, search, wishlist, reviews, VTO, analytics, translations, or personalization.

Do not begin implementation while these are ambiguous.

### 2. Audit before designing

Read the current theme structure and identify:

- Theme architecture and section conventions.
- Existing product-card, quick-add, cart, predictive search, and media components.
- Installed app dependencies and injected scripts.
- Current LCP element, critical CSS, JavaScript cost, image loading behavior, and layout shifts.
- Existing metafields, tags, collections, product types, and variant conventions that can power taxonomy.
- Mobile breakpoints and accessibility patterns.

Reuse stable native components where possible. Do not build a parallel commerce system when Shopify already provides the required behavior.

### 3. Define the experience contract

Produce desktop and mobile mockups covering at minimum:

- Entry state.
- Product-type filters: Sol, Blueblocker, Receta, or configured alternatives.
- Shape/family navigation.
- Highlighted products.
- Product selection state.
- Quick-view or product-detail panel.
- Variant/color switching.
- Add-to-cart feedback.
- Empty, loading, unavailable, and error states.
- Low-performance fallback.

The approved mockup becomes the visual contract. Any implementation deviation must be disclosed before application.

### 4. Select rendering tier

Use the least expensive tier that fulfills the approved experience.

| Tier | Use case | Rendering |
|---|---|---|
| A | Broad device support, fastest launch | Optimized 2D/WebP/AVIF with CSS depth and motion |
| B | Premium interaction without full scene | 2.5D layers, hotspots, parallax, optional product 360 sequence |
| C | Real-time immersive showroom | WebGL scene with glTF/GLB assets and progressive enhancement |

Tier C requires validated 3D assets, a fallback experience, device capability checks, and a performance budget. Never choose real-time 3D only because it appears more impressive.

### 5. Design data architecture

Shopify remains the source of truth.

Recommended fields:

- Product type/use: taxonomy or metafield.
- Shape: standardized metafield.
- Family/model: standardized metafield.
- Showroom eligibility: boolean metafield.
- Showroom priority: integer metafield.
- Shelf/zone assignment: optional metafield.
- 3D model: Shopify file reference or product media model.
- Fallback image: product media or dedicated metafield.
- Marketing line: localized text metafield.

Use collections or Storefront data generated by Liquid to constrain payload size. Do not expose the entire catalog to client-side JavaScript when only a subset is visible.

### 6. Build progressively

Preferred composition:

- Liquid renders semantic structure and initial product data.
- CSS provides the complete usable baseline.
- JavaScript enhances filtering, panels, transitions, 360 interaction, and cart behavior.
- WebGL loads only after intent or when the experience is sufficiently visible and device capability permits it.

Initial HTML must remain navigable if JavaScript fails. Product links and purchase routes must remain available in fallback states.

### 7. Protect conversion

Every product interaction must expose:

- Product title.
- Current price and compare-at price when relevant.
- Selected variant/color.
- Availability.
- Clear purchase action.
- Product-detail link.
- Delivery, warranty, or value proposition only when sourced from current store rules.

Do not hide essential commerce information behind hover. Hover may enhance desktop behavior but cannot be the only interaction path.

### 8. Protect performance

Targets for the showroom route:

- LCP P75 target: <= 2.5 s.
- INP P75 target: <= 200 ms.
- CLS target: <= 0.1.
- Initial route JavaScript: minimize and split by feature.
- No WebGL or 360 payload in the critical rendering path.
- Reserve dimensions for every image, model canvas, drawer, and card.
- Avoid autoplay video in the initial viewport unless specifically approved and measured.

Required techniques:

- Responsive image widths and explicit dimensions.
- WebP/AVIF where supported.
- Lazy loading below the first viewport.
- Preload only the true LCP asset.
- Deferred modules and event delegation.
- `requestAnimationFrame` for visual updates.
- Passive listeners where appropriate.
- Abort stale fetches and interactions.
- Respect `prefers-reduced-motion`.
- Pause animation when hidden or offscreen.

For 3D:

- Prefer glTF/GLB.
- Compress geometry with Draco or Meshopt when compatible.
- Compress textures with KTX2/Basis where practical.
- Limit texture dimensions and material count.
- Use one renderer/canvas when possible.
- Cap device pixel ratio.
- Stop rendering when the scene is idle.
- Dispose geometry, textures, materials, and listeners on section unload.

### 9. Shopify implementation constraints

- Sections must support the theme editor where reasonable.
- Section settings must not permit invalid combinations that break layout.
- Use section IDs to scope CSS and JavaScript.
- Support Shopify design mode and section reload events.
- Use locale files for customer-facing text.
- Avoid blocking third-party libraries from public CDNs when the asset can be bundled or hosted in Shopify.
- Do not duplicate cart logic; integrate with the active theme's cart API and events.
- Variant selection must use current variant data and prevent unavailable purchases.
- Dynamic checkout behavior must remain intact unless intentionally excluded and approved.

## Proposed component model

- `mundo-meller-shell`: semantic page container and configuration.
- `mundo-meller-nav`: product type and shape/family controls.
- `mundo-meller-stage`: 2D, 2.5D, or 3D visual environment.
- `mundo-meller-hotspot`: accessible product trigger.
- `mundo-meller-carousel`: mobile-first discovery rail.
- `mundo-meller-product-panel`: quick-view information and variant controls.
- `mundo-meller-cart-adapter`: integration layer for the current theme cart.
- `mundo-meller-fallback`: low-power, reduced-motion, no-WebGL, or failure state.
- `mundo-meller-analytics`: event contract without sensitive customer data.

## Event contract

Track only events that support decisions:

- `mundo_meller_enter`
- `mundo_meller_filter`
- `mundo_meller_product_view`
- `mundo_meller_variant_select`
- `mundo_meller_360_start`
- `mundo_meller_add_to_cart`
- `mundo_meller_product_open`
- `mundo_meller_fallback_used`
- `mundo_meller_error`

Include product and interaction identifiers, not personal information. Ensure events fire once per intended action.

## Validation gates

### Gate A — before requesting construction authorization

Provide:

- Store and duplicate-theme confirmation.
- Current-state audit.
- Approved visual contract.
- Data mapping.
- Rendering tier and rationale.
- File-level implementation plan.
- Risk register.
- Rollback method.
- Performance budget.

### Gate B — before any Shopify write

State the exact batch:

- Files to create or modify.
- Shopify objects affected.
- Expected customer-visible behavior.
- Known risks.
- Verification steps.
- Rollback steps.

Wait for explicit authorization for that batch.

### Gate C — after implementation

Verify:

- Desktop and mobile layouts against approved mockups.
- Filters and navigation.
- Product and variant accuracy.
- Out-of-stock and unavailable states.
- Add to cart and cart feedback.
- Product links.
- Keyboard navigation and visible focus.
- Screen-reader naming.
- Reduced motion.
- No-JavaScript or enhancement failure path.
- WebGL failure and low-power fallback when applicable.
- Theme editor section reload.
- Console and network errors.
- LCP, INP, CLS, and payload observations.
- No unintended change to the published theme.

## Failure rules

Stop and report before continuing when:

- The identified theme differs from the user-approved theme.
- The theme is published and publication was not authorized.
- Product data cannot reliably map to showroom zones.
- 3D assets are missing, corrupt, excessively heavy, or visually inconsistent.
- The current cart contract is unknown.
- A third-party app conflict affects purchase behavior.
- Performance regression exceeds the agreed budget.
- Mobile layout diverges materially from the contract.

Never conceal a partial failure by presenting only successful screenshots.

## Common mistakes

| Mistake | Correction |
|---|---|
| Building the store as a decorative 3D demo | Start from customer discovery and purchase tasks |
| Loading every product and asset initially | Load only the initial zone and defer the rest |
| Copying desktop to mobile | Design a separate touch-first composition |
| Hardcoding product data | Render current Shopify data and metafields |
| Using hover as the only control | Provide click, tap, keyboard, and focus behavior |
| Adding a second cart implementation | Adapt to the theme's existing cart contract |
| Claiming performance from local perception | Measure and report actual route behavior |
| Applying changes directly to production | Use the authorized duplicate theme and rollback plan |

## Completion standard

The skill is complete only when the experience is visually faithful, commercially functional, responsive, accessible, data-driven, measurable, maintainable, and demonstrably isolated from the published theme until explicit publication authorization.
